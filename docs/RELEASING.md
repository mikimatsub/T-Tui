# Release procedure

GitHub Releases is the primary binary channel. The initial supported targets are Linux x86-64 (glibc, built on Ubuntu 22.04) and Windows x86-64 (MSVC, static C runtime). Native installation requires neither Node nor Rust. ARM and macOS builds are outside the 1.0 support promise.

Native archives and the npm package include collected dependency license/notice texts and Rust standard-library notices. Regenerate them with `python scripts/licenses.py` after dependency or toolchain changes; CI verifies them against the exact locked sources and installed toolchain.

The npm package `ttui` is a convenience for Node users. Install with `npm install --global ttui`. It contains both native binaries, an argument-preserving launcher, MIT license, README and hashes. It has no dependencies, postinstall script or runtime download. CI packs `ttui-VERSION.tgz`, checks its complete file list and binary hashes, installs it without scripts in a temporary directory, then runs the installed command on both platforms. Launcher tests exercise Node 24 and 26 on Linux and Windows; native builds, package installation and publishing use Node 24 LTS. The package engine remains `>=24.21.0`.

WinGet can distribute the Windows zip as a portable installer with the `ttui` alias. The generator writes an actual archive SHA-256 and the tagged GitHub asset URL. A manifest is prepared only for stable versions. Microsoft validation and community-repository review are separate from GitHub publication; availability cannot be promised before acceptance. crates.io source distribution can be added later; Cargo publishing is deliberately disabled for now.

## One-time setup

1. Make the repository public after reviewing the source and history. Public npm provenance, free OSS CodeQL and community WinGet downloads depend on public access. Configure the `release` GitHub environment for tag-only deployment. The publishing job also verifies that the tag points to a commit on protected `main`.
2. Require CI and security checks on `main`, block force pushes and require a PR. Choose required check names from a completed run. Enable private vulnerability reporting. Install/enable Renovate for this repository; a config file alone does not install the app.
3. Establish ownership of the unscoped name `ttui` using the bootstrap procedure below. Availability is not a reservation. Never store a long-lived publish token in this repository.
4. In **ttui** package settings, configure a GitHub Actions trusted publisher for owner `mikimatsub`, repository `T-Tui`, workflow `release.yml`, environment `release`, and allow direct `npm publish`. Confirm the existing repository variable `NPM_PUBLISH_ENABLED=true` after setup; the scoped package's publisher settings do not transfer. Subsequent publication uses GitHub OIDC and provenance. Publishing keeps Node 24 LTS and its bundled npm, while CI also tests Node 26.

## 1.1.0 npm rename: stop before tagging

The package moves from `@mikimatsub/ttui` to `ttui`. After merging the preparation PR, **do not tag `v1.1.0` or trigger npm publication until the maintainer establishes ownership and verifies the new package's trusted publisher**. The current registry probe returns 404 for `ttui`; that does not prove npm will accept the name. Trusted publisher configuration belongs to an existing package's settings, so an unpublished name needs a first publication before that setup can be completed.

1. Log in to [npmjs.com](https://www.npmjs.com) as `mikimatsub`, and use an authenticated npm CLI on a trusted machine. Follow the current [trusted publishing documentation](https://docs.npmjs.com/trusted-publishers/). Complete login and MFA locally; never put tokens or codes in chat or the repository.
2. Bootstrap `ttui@1.1.0` with the complete, tested `ttui-1.1.0.tgz` from the successful merged-main CI run's `npm-package` artifact: `npm publish ./ttui-1.1.0.tgz --access public --ignore-scripts`. Verify the artifact's source commit and contents before publishing. For a local pack, first build both native archives, run `release.py bundle` into `target/npm-stage`, and run `package_smoke.py`; packing `npm/` directly omits both binaries and required notices. If npm offers package creation without publishing, that can establish ownership instead. Prefer supported CI provenance when available; ordinary local CLI publication cannot generate npm provenance, and a GitHub artifact attestation is separate evidence.
3. In **ttui → Settings → Trusted publishing**, add GitHub Actions with owner `mikimatsub`, repository `T-Tui`, workflow filename `release.yml`, environment `release`, and permission for direct `npm publish`. npm currently requires a new trusted publisher to complete its first successful publish within two days; recreate an expired configuration before using it.
4. Confirm `NPM_PUBLISH_ENABLED=true` is still the intended repository gate. If step 2 already published **1.1.0**, npm will reject another publish of that immutable version. For that bootstrap release, set the variable to `false` before tagging so GitHub can publish its assets without attempting npm again; restore `true` for the next unpublished version once its publisher configuration is ready. If ownership was established without consuming 1.1.0, keep `true` and let the tag publish it through OIDC.
5. Only after the ownership and publisher checks above may the maintainer or an authorized follow-up tag `v1.1.0`. Prefer an attested GitHub release tarball for manual publication when a release already exists; creating that release still requires separate authorization to lift this stop.
6. After `ttui@1.1.0` is verified on the registry, run from an authenticated maintainer CLI: `npm deprecate @mikimatsub/ttui "T-Tui has moved: npm install -g ttui"`.

If npm rejects `ttui` as too similar to another name, retain `@mikimatsub/ttui`, report the actual rejection, and prepare the Node 26 change without the rename. A 404 lookup or `npm publish --dry-run` cannot prove name acceptance.

## Before stable 1.0

- Green Linux and Windows unit, adapter, lint, terminal, package and security checks for the exact release commit. Review coverage results for gaps; no arbitrary coverage percentage substitutes for behavior checks.
- A maintainer verifies real-account login/import, restart, refresh, inbox/history pagination, incoming updates, photos, sign-out and account switching on both platforms. Store a redacted checklist with date, version and terminal; never store personal payloads.
- Any advertised mutation requires a deliberately authorized live check: sending to a consenting test contact, Like/Pass, profile edits, unmatch and credit-consuming actions. If a workflow is unverified, keep it labeled experimental or remove it from the stable support promise. Automated tests must not perform these actions.
- Verify current Tinder restrictions and decide whether to distribute an unofficial client. Noncommercial status does not grant API permission. Auto-swipe remains outside 1.0.
- Smoke install the release candidate in a clean Windows user profile and clean Linux environment. Verify runtime imports and executable architecture; record any minimum OS/library requirements actually observed.

## Publish

Finish README and page assets before tagging: the npm package ships the README as of the tagged commit. Reference images with absolute `https://raw.githubusercontent.com/mikimatsub/T-Tui/main/docs/assets/...` URLs using stable, version-independent names (`tour.webp`, `inbox.png`, `discover.png`, `chat.png`, `profile.png`), never tag-pinned URLs, so replacing a file under the same name updates the npm page without a release. Do not delete an asset that an already-published README references (for example `demo.gif`, used by 1.0.0); check that every image URL returns 200.

Update `Cargo.toml`, `Cargo.lock`, `npm/package.json` and changelog together. `python scripts/release.py check --tag vVERSION` rejects mismatches. Merge the reviewed change with required checks passing, tag that commit and push the tag. The workflow reruns CI and security from the tag, then enters the protected release environment. No manual dispatch can silently publish the default branch.

The release workflow verifies checksums, attests artifacts, and creates the GitHub release, including the tested npm tarball as a downloadable asset. When `NPM_PUBLISH_ENABLED=true`, a separate job publishes that tarball to npm (`next` for release candidates, `latest` for stable). Otherwise npm publication is explicitly skipped; a GitHub asset is not an npm registry release. Configure native-release prerequisites before pushing a tag. Registry versions are immutable: if publication succeeded, do not try to overwrite that version. If a later step fails, inspect upstream state and recover only the missing operation from the original verified run. Do not rebuild different binaries under an existing tag.

npm-only recovery: if the GitHub release is complete but npm publication failed, land any workflow fix on `main`, push a new tag `<tag>-npm-recovery` at that `main` commit (never move the release tag), then run `gh workflow run release.yml --ref <tag>-npm-recovery -f release_tag=<tag>`. The `npm-recover` job downloads the tarball from the existing release, verifies its attestation against the original tag, and publishes it with provenance through trusted publishing. It does not rebuild anything.

After GitHub publication, the workflow downloads the actual public assets without authentication on both platforms. It verifies the archives and npm tarball against GitHub attestations for the exact release tag, source commit and signing workflow, then runs the native executable and the installed npm shim with isolated offline data. npm publication waits for these checks. Once npm publication is enabled, separately install from the registry on both platforms and inspect npm provenance. Only then call that channel verified.

For WinGet, validate the generated manifest with `winget validate` using the installed command's help. Then test installation from that manifest in an isolated Windows environment and submit it to `microsoft/winget-pkgs`. The GitHub asset must already be publicly downloadable. Do not submit a placeholder URL or hash. The manifest generator is preparation, not evidence of acceptance.
